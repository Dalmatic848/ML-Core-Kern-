# Как вносить изменения

`main` — защищённая ветка. Прямые коммиты в `main` не делаются — только
через pull request.

## Процесс

1. Ветка от `main`: `git checkout -b <тип>/<короткое-описание>`
   (например `feat/add-swin-t`, `fix/oom-effb3`).
2. Изменения + коммиты в стиле `тип: описание на русском`
   (`feat:`/`fix:`/`refactor:`/`docs:`/`chore:`/`test:` — см. `git log`
   для примеров).
3. Перед PR — обязательно:
   ```bash
   ruff check .
   pytest
   ```
   (то же самое проверяет CI и, если установлен, pre-commit —
   `pre-commit install` один раз после клонирования.)
4. Если менялась таксономия (`src/taxonomy.py`,
   `soft_labels_config.json`): `python3 scripts/validate_taxonomy.py`.
5. Если добавлен/изменён эксперимент, который дал новый лучший результат —
   обнови README.md («Лучшие результаты», «Хронология экспериментов»).
   Агент `experiment-analyst` может подготовить черновик записи.
6. Открой PR в `main`. CI (ruff + pytest) должен быть зелёным.

## Что НЕ коммитить

- `data/`, `results/`, `logs/`, `models/*` (кроме `models/README.md`) —
  всё это в `.gitignore` намеренно (см. README «Воспроизводимость»).
  Эксперименты воспроизводятся из `experiments/*.yaml`, а не из сырых
  артефактов.
- Ноутбуки — проект отказался от них (см. `git log` — commit "chore:
  удалить мусор"), не добавляй новые `.ipynb` вместо `.py`-скриптов.

## Структура коммита при рефакторинге

Если меняешь что-то, что затрагивает несколько файлов сразу
(например правишь `src/models/registry.py` и все его вызовы) — один
логический коммит на одно изменение, не россыпь мелких. См. `git log`
для примера дробления на коммиты при исходной чистке репозитория.
